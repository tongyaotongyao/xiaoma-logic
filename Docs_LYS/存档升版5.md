# 存档升版 5：进行中的对局真正能续上

> 对应根目录文档 `ADVENTURE_DESIGN.md` 第 6.3 节「存档」。那篇是需求，这篇是我们落地后的实现记录与取舍说明。
> 改动范围：`XiaomaSaveGame.h`、`XiaomaGameMode.h/.cpp`、`XiaomaPuzzle.h/.cpp`、`XiaomaPuzzleTests.cpp`。没有动 `levels.json`。

## 1. 这次修的是两个漏洞，不只是体验

升版之前，进行中的对局只存了 4 个字段：`ActiveCells / ActiveHintsUsed / ActiveWrongAttempts / Lives`。棋盘能恢复，但**步数、主角位置、提示星、道具、机关状态全都不存**。这直接造成两个可以让玩家绕过规则的口子：

| 漏洞 | 怎么发生的 | 后果 |
|---|---|---|
| 三星白送 | `StartLevel` 恢复棋盘但把 `StepCount` 归零 | 走到超过 `par` 就退出重进，棋盘还在、步数从 0 起算，「步数达标」那颗星白拿 |
| 提示星可刷 | 机关状态不存，宝箱回到未开启 | 退出重进再解一次符文/石碑，又能领一颗提示星；反复操作等于无限提示 |

另外还有一条更隐蔽的：**走格子不触发存盘**。`SaveProgress()` 全项目 17 处调用点，全在"放马、撤销、开箱、扣命"这类事件上，`OnHerdsmanCellChanged` 里只加了步数。所以即便字段补齐，退出前最后几步也会丢，符文踩到一半的进度也不在盘上。

## 2. 存档结构（`LevelRevision` 4 → 5）

```
XiaomaSave::LevelRevision = 5
```

新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ActiveStepCount` | int32 | 已走格数，三星判定用 |
| `ActiveHintTokens` | int32 | 手里还没用的提示星 |
| `ActivePettedMask` | int32 | 抚摸过的小马位掩码，纯表现 |
| `ActiveHasClover` | bool | 四叶草是否还挂着 |
| `ActiveHerdsmanCell` | FIntPoint | 主角所在格，`(-1,-1)` 表示没有记录 |
| `ActivePickupCollected` | `TArray<bool>` | 每关道具的拾取位图，顺序同 `levels.json` 的 `items` |
| `ActiveMechanismStates` | `TArray<uint8>` | 各机关状态的扁平字节流 |
| `ActiveLevelFingerprint` | int32 | 冒险布局指纹 |

`Lives` 按设计案第 167 行改为「只记录当前关卡的生命」，进入新关卡时被 `adventure.lives` 重置；不再额外加一份 `ActiveLives`，避免两份生命互相打架。

### 为什么不直接存 `TArray<TArray<uint8>>`

`FXiaomaUndoSnapshot::MechanismStates` 用的是嵌套数组，但那是普通 C++ 结构体。`UPROPERTY` **不支持嵌套容器**，写成 `TArray<TArray<uint8>>` 反射编译不过。所以改用扁平流：

```
[1 字节长度][内容][1 字节长度][内容]...
```

由 `FXiaomaMechanismStateCodec::Encode/Decode` 负责。长度上限 255，目前最长的是符文宝箱的 5 字节。解码时一旦发现截断就**整份拒绝**——宁可整关重开，也不要恢复出"一半正常一半诡异"的机关状态。

## 3. 关卡指纹：为什么必须加

恢复机关状态是**按索引**配位的：`SpawnAdventureActors` 的生成顺序固定为「障碍 → 宝箱 → 道具」，存档也按这个顺序写。麻烦在于——只要关卡数据增删一个障碍，第 3 个机关在旧存档里存的是宝箱状态，恢复时就贴到了另一个宝箱上。

所以存档里带一个布局指纹（`FXiaomaPuzzle::AdventureFingerprint`，FNV-1a）：只覆盖会影响配位的字段——障碍格子、宝箱格子/谜题类型/规则索引/符文顺序/石碑位置、道具类型与格子。指纹对不上，整局丢弃，不进游戏。

读取时机在 `BeginPlay`：先 `MigrateLevelRevision()`，再把 `ActiveLevel` 夹到 `UnlockedLevel` 以内（顺手补掉了之前记下的那个隐患），最后比对指纹。

## 4. 存盘时机

保留原来 17 处事件驱动调用点不变，新增三类：

| 时机 | 做法 | 原因 |
|---|---|---|
| **走格子** | 标脏 + 每 **2 秒**最多落盘一次 | `OnHerdsmanCellChanged` 会改步数、踩亮符文、拾取道具，这些都不经过其他存档点 |
| **离开进行中状态** | `SetScreen` 在 `Screen == Playing → 其他` 且 `bHasActiveRound` 时先落盘 | 暂停、回菜单、通关、失败都走这里 |
| **世界关闭** | `EndPlay`，且只有 `bRoundDirty` 才写 | 直接关窗口没有暂停流程，不补就丢最后 2 秒 |

`SetScreen` 里那句条件是必要的：通关/失败时代码是**先**把 `bHasActiveRound` 置 false **再** `SetScreen`，如果没有这个守卫，flush 会把已结束的对局重新写回存档，下次"继续游戏"就回到已通关的那一关。

2 秒的取舍：最坏丢约 6 格移动记录。之所以不做成"每进一格就存"，是因为 `SaveGameToSlot` 每次会重写整个文件，一格约 0.33 秒，等于每秒写三次盘。

## 5. 恢复顺序（有坑）

```
ResetBoard / 恢复 Cells
  -> Board->BuildBoard
  -> SpawnAdventureActors      // 机关、道具在这里 new 出来
  -> TeleportToCell(存档格)
  -> RestoreActiveRound        // 必须在这之后，否则没有对象可贴状态
  -> SetScreen(Playing)
  -> RefreshBoardAndUI
  -> SaveProgress
```

`SpawnAdventureActors` 末尾会 `NotifyMechanismsBoardChanged()`，规则宝箱可能根据恢复出来的棋盘先自动变成"已解锁"。随后 `RestoreActiveRound` 用存档状态覆盖，存档是权威的，这个先后顺序是安全的。

## 6. 已知限制

- **撤销历史不跨会话**。`UndoHistory` 不落盘（会随步数线性膨胀），所以重开游戏后第一次按 `Z` 没有反应。
- **2 秒窗口**。崩溃或强杀进程时最多丢约 2 秒的移动。
- **`.sav` 不是原子写**。UE 的 `SaveGameToSlot` 直接覆盖文件，正好在写盘瞬间断电理论上会坏档。现有代码对此有兜底：`LoadGameFromSlot` 返回空就 `CreateSaveGameObject` 新建，不会崩，只是丢一次进度。
- **旧档会丢一次进行中的棋盘**（`LevelRevision` 4 → 5）。解锁进度、星级、好感度、连胜、设置全部保留。

## 7. 验证

`python` 的关卡校验（25 关 0 错误）不受影响；UE 自动化测试 `XiaomaLogic.Puzzle.AllLevels` 通过，新增断言：

- 迁移：rev 4 的进行中棋盘、步数、机关状态、主角格全部被清掉，`UnlockedLevel / Affection / StarsByLevel` 保留；
- 已经是 rev 5 的续局原样保留；
- 扁平状态编解码 round-trip（空状态、5 字节宝箱状态、截断数据必须整份拒绝并清空输出）；
- 布局指纹：同一关稳定、不同关不同、加一块障碍就会变；
- 续局判定 `UXiaomaSaveGame::CanResume`：关卡不符、格子数不符、生命为 0、指纹过期，四种情况都必须拒绝。

`CanResume` 特意从 `AXiaomaGameMode` 挪到了存档对象上，就是为了让它能在没有 World 的自动化测试里直接断言。

## 8. 还没验证的

**真机时的"退出→再进"没有实测过**，只验证到逻辑层。需要人工确认的四件事：

1. 走到一半退出，再进"继续游戏"，人是否站在离开的位置、步数是否接着算；
2. 符文踩到第 2 个退出，再进是否还在第 2 个（宝箱顶上宝石顺序应保持）；
3. 拿过提示星的宝箱，退出再进是否仍然处于已领取（不能再领一次）；
4. 通关后退出再进，是否不会回到已通关的那一关。

## 9. 下一步

存档这条链通了之后，机关状态统一走 `SaveState/LoadState`，后面新增的捣蛋鬼、冰面、木桥只要实现这两个函数就自动进存档——不需要再动 `XiaomaSaveGame`。
