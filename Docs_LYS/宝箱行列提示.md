> 状态：已完成。编译通过，`XiaomaLogic.Puzzle.AllLevels` 通过（Result=成功），25 关数据校验全过，86 个 Python 用例未受影响（本次没动数据）。2026-11-28。
> 上游：`组合宝箱.md` 第 3 节（规则开箱的运行时），本文只谈提示文案与视觉指路。

## 1. 玩家反馈的问题

旧文案是这么拼的：

```cpp
FString::Printf(TEXT("在%s第 %d 格放对小马即可开启"), RuleText, Stage->RuleIndex + 1);
// RuleText = "对应行" / "对应列" / "对应颜色区域"
```

`RuleIndex + 1` 是**行号 / 列号 / 色区编号**，但句式把它说成了"第几格"。三处指代都是错的：

| 想表达 | 旧文案读起来 | 后果 |
|---|---|---|
| 第 3 行摆对 | "对应行第 3 格" | 读成"这一行第 3 列"，指向另一格 |
| 第 3 列摆对 | "对应列第 3 格" | 读成"这一列第 3 行"，指向另一格 |
| 粉色草皮摆对 | "对应颜色区域第 3 格" | 色区编号不是格子序号，纯错 |

另外"对应行/对应列"对玩家没有指代对象——谁是"对应"的那条？所以看到这句话只能靠猜。第 24、25 关的规则段是 `col`，玩家一定会撞上这句。

## 2. 新文案

判定条件没变（该行/列/色区的**正解格**上摆着小马就开），只改说法：

| 段类型 | 文案 |
|---|---|
| 行 | `宝箱上锁中：把第 3 行的马摆对即可开启` |
| 列 | `宝箱上锁中：把第 3 列的马摆对即可开启` |
| 色区 | `宝箱上锁中：把粉色草皮上的马摆对即可开启` |

- 多段宝箱照旧带前缀：`第 2/3 道锁：把第 3 列的马摆对即可开启`；
- 说"摆对"而不是"放一匹"：每行/列/色区本来就只放一匹，随便摆一匹不算数，判定看的是正解格；
- 色区的颜色名与 HUD 六色图例、召唤轮盘同一套（蓝/棕/粉/红/黄/薄荷），宝石这时也已经染成同一个颜色，两边对得上。

**计数约定**：行从最上面数，列从最左边数。相机 `yaw=90°` 朝 +Y、俯角 -56°，屏幕上 -X 在右侧，而世界 `X=(5-列)×112`，所以列号从左往右递增。这与 `H` 键提示星那句"第 x 行，第 y 列"用的是同一套。

## 3. 视觉：地板缝里的两条金线

只靠文字还是得数行列，所以当前段是**规则开箱 + 指定行/列**时，在那条线两侧的地板缝里嵌两条金线：

| 项 | 取值 |
|---|---|
| 颜色 | `(226, 180, 82)`，与宝箱盖的金色同一路 |
| 尺寸 | 长 672（整条 6 格含两侧半格）、宽 5、高 3.5 |
| 高度 | 中心 z≈9.6（地板顶面 8，只露一点点，不会被当成障碍） |
| 位置 | 目标行/列的两侧边缘（±半格），正好夹住这一条线 |

几条规则：

1. **只在当前段亮**：`stele → rule` 这种链（24、25 关）在石碑段不会亮，轮到规则段才出现——金线一出现就等于说"现在该看这条线了"；
2. **色区不上线**：色区块已经有宝石染色指路，再画一圈线反而更糊；
3. **组件恒为 2 个**：首次需要时创建，之后换行/换列只改 `SetRelativeLocation` 与 `SetRelativeScale3D`；创建后手动设 `Movable`，避免运行时挪静态组件报警；
4. **纯视觉**：不进存档、不进指纹、不参与撤销——它完全由 `StageIndex` 推出来，`LoadState` 之后 `RefreshVisuals()` 自然就对了。

实现只有一处：`AXiaomaChest::RefreshLineHint()`（`XiaomaMechanism.cpp`），由 `RefreshVisuals()` 末尾调用，所以开局、换段、读档、领取都会自动刷新。

## 4. 已知取舍

- **不做"靠近才显示"**：提示文字本来就是按 `E` 才出，金线常显可以让人先知道"这个宝箱在盯哪一行"，不用先跑到跟前按一下。以后嫌吵，只要在 `bWantLine` 里加个距离判断即可，不用动结构。
- **不做脉动/呼吸动画**：`AXiaomaChest` 目前不开 Tick，为两条静态线开 Tick 不值得。
- **金线会穿过木桥/冰面**：那两样都在 z≥10，金线在 9.6，被压住时看不全，但不影响判定；目前 `row/col` 规则的关里还没有桥或冰压在目标线上。
