## 2. 怎么用

```bash
# 看当前存档（不改）
python Tools/unlock_save.py --dry-run

# 解锁全部 25 关（默认行为）
python Tools/unlock_save.py

# 只解锁到第 10 关
python Tools/unlock_save.py --unlock 10

# 顺手把所有关卡标成三星（只影响星级，不影响解锁）
python Tools/unlock_save.py --stars 3
```

写盘前会自动在存档旁生成 `XiaomaLogicProgress.sav.bak-<时间戳>`；写完会重新解析一遍做自检。

> **运行前请先关掉编辑器/游戏。** 游戏运行中存档由内存里的 `UXiaomaSaveGame` 持有，
> 下一次 `SaveProgress()` 会把内存值写回，覆盖工具的改动。

## 3. 存档格式（UE 5.5）

`Saved/SaveGames/XiaomaLogicProgress.sav` 是 UE 的 GVAS 二进制：

```
"GVAS"
SaveGameFileVersion / PackageFileUEVersion(4) / PackageFileUEVersion(5)
FEngineVersion：Major(u16) Minor(u16) Patch(u16) Changelist(u32) Branch(FString)
CustomVersionFormat(i32) + 条数(i32) + N × (GUID 16B + 版本 i32)
存档对象类名(FString) + 一个恒为 0 的字节
属性流 … "None" 结束
```

属性 tag（UE 5.3 起改成「完整类型名」，与网上多数旧资料不同）按以下顺序写：

```
名字 FString
完整类型名：FString 类型名 + i32 参数个数 + 递归参数
            例：IntProperty → "IntProperty" + 0
                ArrayProperty<IntProperty> → "ArrayProperty" + 1 + ("IntProperty" + 0)
长度 i32
标志 u8   0x01 带 ArrayIndex / 0x02 带 PropertyGuid / 0x04 带扩展 / 0x10 布尔为真
可选 ArrayIndex(i32)、PropertyGuid(16B)
值（长度字节）；布尔属性没有值，真值在标志位里
```

早先按「名字、类型、长度、ArrayIndex、PropertyGuid」这套旧布局去读会整体错位，
表现为第一个属性能读出名字、第二个属性长度变成 `1869377109`——那是把 `UnlockedLevel`
的字符当成了长度。工具里已按新布局实现，并以「能一路解析到 `None` 结束」作为对齐判据。

## 4. 为什么不用「改 CDO 默认值」或「加作弊开关」

- 存档里 `UnlockedLevel` 是唯一决定关卡按钮是否可点的字段（`XiaomaHUDWidget.cpp:161`），
  直接改它最小、最直接；
- 改 C++ 默认值只对全新存档生效，已有存档会把旧值读回来；
- 加 Exec 作弊命令要重新编译，且仍需在游戏里敲一次，不如这个工具能一条命令重复使用
  （换机、清档、重装后都适用）。

## 5. 已知限制

- 只处理定长就地改写：`StarsByLevel` 不是 25 项时会直接报错退出，不会改文件长度；
- 不支持带「属性扩展」（标志 `0x04`）的属性，遇到会报错而不是猜；
- 存档缺失时报错退出，提示先启动一次游戏生成。

## 6. 顺带发现的一个问题

当前存档 `ActiveLevel = 2` 且 `bHasActiveRound = true`，而 `UnlockedLevel` 原本只有 2。
也就是说**进行中对局的关卡号有可能超过已解锁进度**（这里两者相等，还没暴露）。
`XiaomaGameMode::GetCurrentLevelNumber()` 会优先返回 `ActiveLevel`，
若某次存档里 `ActiveLevel > UnlockedLevel`，启动时会直接进入未解锁的关卡。
建议后续在读取存档时夹一下：`ActiveLevel = FMath::Min(ActiveLevel, UnlockedLevel)`。
本次未改动这个行为，只做记录。
