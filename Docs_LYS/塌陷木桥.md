# 塌陷木桥（M4）

> 状态：已完成，编译通过，`XiaomaLogic.Puzzle.AllLevels` 通过，62 个 Python 用例全过，25 关校验全部通过。2026-11-28。
> 策划案出处：`ADVENTURE_DESIGN.md` §4「阻碍与机关」、§6.1 `bridges` 字段、§8 检查项 2/3、§11 M4。
> 与策划案的取舍见第 6 节。

## 1. 规则

木桥一格宽，初始是完好的木板：**能走进去、能站在上面、能原路走回来**。
但只要**离开那一格**，桥就塌成坑，此后（包括主角和木箱）都不能再进入。

关键的一点是塌陷时机：**踩上去不塌，离开才塌**。这样玩家不会在走到格子中间时脚下突然消失，视觉上也是"身后断了"而不是"凭空掉下去"。

桥塌了不会死，也不会扣命，只是**退路没了**。要反悔就按 `Z`——塌陷的那一刻已经压了快照，撤销会让**这次过桥当成没发生**：人退回上桥前那一格、步数也退回去、桥恢复完好（策划案 §4 明确要求 `Z` 能把桥恢复），可以换条路再走。

## 2. 数据结构

```json
"adventure": {
  "bridges": [[4, 5]]
}
```

- 只记格坐标，顺序即生成顺序（见第 3 节的存档下标约束）。
- 桥是**机关**（`AXiaomaBridge`，继承 `AXiaomaMechanism`），因为它有状态（完好/已塌），要进撤销快照和存档，1 字节（`0` 完好 / `1` 已塌）。
- 桥也进 `AdventureFingerprint`：桥的数量一变，存档里"第几个机关"就错位了，旧续局必须作废。

## 3. 实现要点

**状态机（`XiaomaBridge.h/.cpp`）**

| 事件 | 行为 |
|---|---|
| 主角进入桥格 | 记 `bHerdsmanOn = true`；把主角**上桥前站的格**记进 `ApproachCell`（读 `Herdsman::GetPreviousCell()`）；广播 `OnStepped` → GameMode 只给提示，**不压快照**（桥还没塌，没有需要复原的东西） |
| 主角离开桥格 | `bHerdsmanOn = false`；若桥还完好，先广播 `OnCollapsing` → GameMode 压一条"桥还在"的快照，然后 `Collapse()` |
| 塌陷后 `BlocksCell()` | 返回 true，主角与木箱都进不去 |
| `SaveState/LoadState` | 1 字节；`LoadState` 顺便把 `bHerdsmanOn` 清掉 |

**撤销落点**：`OnBridgeCollapsing` 压完快照后，直接把栈顶那一条改写成"过桥之前"——`HerdsmanCell` 换成 `ApproachCell`、`StepCount` 减 2（进桥格一步 + 离桥格一步）。所以按一次 `Z` 的净效果是：**人回到上桥前、步数回到上桥前、桥完好像没被踩过**，和"这次过桥没发生"完全一致。

`ApproachCell` 由谁提供：`AXiaomaHerdsman` 新增 `PreviousCell`（`UpdateCurrentCell` 在赋值**之前**记下来路，广播期间各机关读到的都是"进入这一格之前"的位置）。传送（撤销/读档/挨撞弹回）会把 `PreviousCell` 和 `CurrentCell` 一起对齐，避免把传送前那一格当成来路；否则撤销后随便走一步就可能误判上桥格。

**为什么不广播"离开"事件**：机关的接口只有 `OnHerdsmanEnterCell(NewCell)`，但 GameMode 对**每一格变化**都会广播给所有机关，所以桥自己能判断"新格不是我的格、而我上一帧是被人踩着的"——这就是离开。

**传送必须手动同步**：`TeleportToCell`（撤销、读档、挨撞弹回）不广播"进入新格"。如果不同步，桥会以为自己还被人踩着，下一步就误判"人离开了"把桥塌掉。所以 GameMode 有个 `SyncBridgeOccupancy()`，在撤销之后、挨撞之后、读档之后各调一次，只更新"人在不在桥上"，**不触发塌陷**。

~~同步时如果发现"撤销把人恰好放回了一座完好的桥上"，会补压一个撤销点。~~ **这条已废弃（2026-11-28 修）**：撤销本身就是"从历史里取出一个状态"，若恢复出来的位置上人正站在完好的桥上，再压一条快照，栈顶就被"刚恢复的状态"占住；之后每次按 Z 只是把同一条快照弹出再压回，画面毫无变化，更早的历史永远走不到（表现就是"上了桥以后只能撤销回桥上"）。

现在的做法是：撤销点只在**塌陷那一刻**压（`OnCollapsing`，此时桥还没变），一次过桥正好对应一条；`SyncBridgeOccupancy()` 只同步标志，不碰历史。这样"再走一次没得撤"的缝也不存在了——每次塌陷都会重新压。

**生成顺序**：桥排在 **所有已有机关之后**（障碍 → 宝箱 → 木箱 → 捣蛋鬼 → 木桥）。机关状态是按 `Mechanisms` 下标顺序写进存档的，新类型只有往后追加，老关卡（没有桥）的存档下标才不会错位。

**视觉**：三块木条 + 塌陷后的两层深色圆盘（不做真凹面）。木板顶面 z=13，和冰面同高，不埋脚；坑贴地 z≈8.6，才不会陷进地板里看不见。

## 4. 关卡

| 关 | 桥 | 障碍 | 最短/par | 设计意图 |
|---|---|---|---|---|
| 18 | (4,5) | (5,4) | 19 / **25** | **首现**。右下角那匹马只能从 (4,5) 过桥上 (5,5)，而 (5,4) 被石头堵住，所以这一格天然是**最后一站**——过桥就没回头路。教"桥只走一次" |
| 19 | (3,3)、(5,4) | (2,4)、(2,5)、(4,3)、(5,5) | 19 / **25** | **双桥围区**。(3,4) 所在的小房间四周围死，只在 (3,3) 和 (5,4) 各留一座桥：从一头进、另一头出，两座桥都会塌，房间再也进不去。顺序是"先把外面做完，再进房间" |
| 20 | (4,5) | (1,5)、(2,2)、(3,1)、(4,0)、(5,4) | 23 / **30** | **综合**。仍然是右下的单程口袋，左侧用障碍拉出一条长绕路，步数从 19 涨到 23 |

三关的桥都是**必要**的：把桥当成墙来搜可达性，都会有关键正解格到不了。这条写进了 Python 用例 `test_bridge_levels_need_the_bridge`。

## 5. 校验工具

`Tools/validate_adventure.py`：

- `bridges` 从"未实现机关"名单移除，正式解析，棋盘预览新增 `=` 符号。
- **可达性与 `min_steps` 都带上了桥状态**：状态从 `(格, 已踩目标)` 扩成 `(格, 已踩目标, 已塌桥掩码)`。6 座桥最多 64 个掩码，Dijkstra 规模完全够用。离开桥格的那一刻把该桥的位打上，之后这格就是坑。
- 新增守卫（都是错误，不是提示）：

| 检查 | 理由 |
|---|---|
| 桥在正解格 / 桥就是起点 | 桥要放小马，塌了没法完成；起点踩上去开局就塌 |
| 桥与障碍、道具、宝箱同格 | 站不下 / 桥塌了东西掉坑里 |
| 冰面与木桥同关 | 滑行冲上桥会把桥踏塌再回不去，规则解释不清 |
| 木箱与木桥同关（含压力板在桥上） | 箱子推上桥算不算踩塌，规则还没定义 |
| 符文/石碑宝箱与木桥同关 | `runes_solvable` 不了解桥状态，顺序校验会失真 |
| 巡逻路线经过桥格 | 桥塌后捣蛋鬼会站在坑上，也不该让它替玩家把桥走塌 |

## 6. 与策划案的取舍

**木桥首现从第 16 关挪到第 18 关。** 策划案 §4 表格写的是第 16 关，但我们在 16~17 关已经放了冰面（策划案也给冰面写了第 16 关），两套"改变走位"的规则挤在一起会让玩家一次学两件事。§7 的节奏表本来就是 16~20 一起讲"路线顺序本身成为谜题"，所以按 16~17 冰面、18~20 木桥排，与节奏表一致，只和 §4 的表格差两关。

**冰面与木桥不同关**（策划案没提）。理由是滑行时玩家没有控制权，冲上桥把桥踩塌却停不下来，这种"手不能动但世界变了"的组合很难解释。真要组合，需要先定义"滑行经过桥格算不算用掉"，那是另一个规则问题。

**木桥不参与符文/石碑与推箱**，同样是因为它们的校验逻辑各自独立，先不做交叉。
