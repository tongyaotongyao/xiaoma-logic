# 组合宝箱（M4）

> 状态：已完成，编译通过，`XiaomaLogic.Puzzle.AllLevels` 通过（EXIT CODE 0），81 个 Python 用例全过，25 关校验全部通过。2026-11-28。
> 策划案出处：`ADVENTURE_DESIGN.md` §5「宝箱谜题」中「四种可以组合」与 §6.1 `puzzle.then` 字段、§7 第 22 关示例。
> 前提：本文档假定三星规则已经改为「集齐本关宝箱」（见 `三星规则.md`），否则组合宝箱对玩家没有分量。

## 1. 规则

一个宝箱可以有多段谜题，**严格串行**：

1. 只有**当前段**的机关响应输入。后面几段的符文/石碑/压力板照样显示，但压暗到 30%，表示「还没轮到」；
2. 当前段做完，下一段亮起来，提示文字会告诉玩家现在要做什么；
3. **最后一段完成**，宝箱才真正打开，按 `E` 领取；
4. 提前踩后面那段的符文：只给一句「这个符文还没醒——先把前面那道锁打开」，不记进度。

为什么不做「任意顺序、各记进度」：那样「先石碑再符文」的顺序就不成立了，玩家可以乱序提前做完，链式设计想表达的「先后关系」全丢；而且每段都要各存进度、各写提示，撤销时容易错位。

段数上限 **3 段**。再多玩家记不住，也说明这一关该拆了；解析时超出的段只打日志丢掉，校验工具会直接报错。

## 2. 数据结构

```json
"chests": [{
  "cell": [0, 5],
  "reward": "hint",
  "puzzle": {
    "type": "stele",
    "clue": { "text": "宝箱压在最右上角那一格，一圈栏杆把它围住了", "cell": [3, 1] },
    "answer": [0, 5],
    "then": { "type": "runes", "order": [[2, 4], [2, 5]] }
  }
}]
```

- `puzzle` 顶层是**第 1 段**，`then` 是第 2 段，`then.then` 是第 3 段。
- 每一段的字段和原来单段时完全一样（`type`/`target`/`index`/`order`/`clue`/`answer`/`plate`）。
- 没有 `then` 的宝箱就是单段，**旧数据一行都不用改**，行为不变。

C++ 侧把原来平铺在 `FXiaomaChestDef` 上的字段收进了 `FXiaomaChestStage`：

```cpp
struct FXiaomaChestStage { PuzzleType, RuleType, RuleIndex, RuneOrder, SteleCell, ClueText, SteleAnswer, PushPlate };

struct FXiaomaChestDef
{
    FIntPoint Cell;
    EXiaomaItemType Reward;
    TArray<FXiaomaChestStage> Stages;   // 至少一段
    int32 NumStages() const;
    const FXiaomaChestStage& StageAt(int32) const;
};
```

解析入口 `ParseChestStage()`（`XiaomaPuzzle.cpp` 匿名命名空间）递归处理 `then`，并在超过 3 段时打 `Warning`。指纹改成「段数 + 每段全部字段」——改顺序、加一段都会让旧续局失效。

## 3. 运行时（`AXiaomaChest`）

**状态**

| 成员 | 含义 |
|---|---|
| `StageIndex` | 已完成的段数；等于 `Stages.Num()` 表示全部解开（`IsUnlocked()`） |
| `StageProgress[]` | 每段一字节：符文=点亮数、石碑=`0` 未读/`1` 读过/`2` 挖出、规则与推箱=`0`/`1` |

用「已完成段数 + 每段一字节」而不是一堆并列 bool，是因为撤销要能退到任意中间状态：`LoadState` 只要把 `StageIndex` 和这一串字节放回去，画面自然对得上。

**四类触发都只认当前段**

| 谜题 | 触发 | 完成条件 |
|---|---|---|
| 规则 | `OnBoardChanged` 判当前段的行/列/色区 | 该格摆对小马 |
| 符文 | `OnHerdsmanEnterCell` 判当前段 `RuneOrder` | 点亮数 = 符文个数；踩错清零**只清当前段** |
| 石碑 | `TryInteract` 判任意段的石碑格，但只有当前段记「读过」 | 读过 → 到宝箱格按 E 挖出 |
| 推箱 | `GameMode::RefreshPushPlates` 只在 `IsPushStageActive()` 时看板 | 箱子压上压力板 |

**视觉**：每段建一套部件（`FXiaomaChestStageVisuals`，按 `StageIndex` 取用）。已完成的符文段整片点亮，当前段按进度点亮，后续段全暗；顺序宝石只显示当前段；石碑的浮空符印在没轮到时会缩小。

**存档格式**：`[2][StageIndex][是否领取][每段进度...]`。首字节写 `2` 而不是布尔值，是为了和旧格式（首字节是 `bUnlocked` 的 0/1）区分开；旧格式按单段兜底解释，`LoadState` 不会崩。

**撤销**：宝箱状态本来就在 `MechanismStates` 里，段式状态跟着一起进出快照，不需要额外处理。

## 4. 第 22 关

按策划案 §7 的示例配：石碑给线索 → 开门 → 挖宝 → 踩符文。

| 项 | 内容 |
|---|---|
| 围栏 | 色区 0（右上三格 `(0,3)(0,4)(0,5)`，含正解格 `(0,4)`），开关 `(4,2)` |
| 宝箱 | `(0,5)`，埋在围栏区域内——不开门走不进去 |
| 石碑 | `(3,1)`，线索「宝箱压在最右上角那一格，一圈栏杆把它围住了」 |
| 符文 | `(2,4)` → `(2,5)`，两段链的第二段 |
| 路线 | 读石碑 → 走到 `(4,2)` 踩开关开门 → 进区域挖出宝箱 → 回 `(2,4)(2,5)` 按顺序踩亮 → 领奖 |
| par | 最短 22 步，par 29（含宝箱路线，见 `三星规则.md` 第 3 节） |

顺带的好处：`(0,3)` 那颗四叶草也在围栏里，开门的同时能顺手捡到。

## 5. 校验工具

`Tools/validate_adventure.py` 新增/修改：

| 检查 | 说明 |
|---|---|
| `puzzle_stages()` | 递归展开 `then` 链，全工具统一用它遍历段 |
| 段数上限 | 第 4 段起报错「组合宝箱最多 3 段」 |
| 每段格子冲突 | 符文格、石碑格**每一段**都要查障碍/宝箱/道具/正解格/互相重复（原来只查顶层 `puzzle`，第二段完全没人管） |
| 符文顺序可走 | `runes_solvable` 对每一段都跑一遍 |
| 宝箱可完成性 | 每个宝箱格、每段的石碑格/符文格/压力板格，都必须在「围栏全开」的可达集合里，否则报「这个宝箱开不了」 |
| par 目标 | `chest_route_cells()` 把上面这些格并进 par 的必踩集合 |

「宝箱可完成性」这条是从三星规则衍生出来的硬要求：一个走不到的宝箱 = 这一关永远拿不到三星，必须在数据阶段拦住。

## 6. 未做与已知取舍

- **不做「任意顺序」**：见第 1 节。
- **不做跨宝箱链**：两个宝箱之间没有顺序关系，各开各的。
- **推箱段的可完成性**是按「玩家自己站到压力板」近似的，`box_push_states` 只在单箱推演里验过「有箱子能推到板」，多段链里如果推箱段排在后面，没有单独再模拟一遍推箱过程。22~25 关目前没有「推箱作为后续段」的配置。
